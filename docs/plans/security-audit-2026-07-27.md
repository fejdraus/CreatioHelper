# Аудит безопасности, 27 июля 2026

Проверка проведена по коммиту `9d32f85`. Каждый кандидат, найденный автоматическим
поиском, проверялся вручную — здесь только подтверждённое. Отдельным разделом
записано, что проверено и оказалось в порядке, чтобы это не пришлось перепроверять.

## Исправлено в ходе аудита

### Выход за пределы папки по запросу от удалённого устройства

`BlockRequestHandler` строил путь из `request.Name`, присланного пиром, и проверял
результат так:

```csharp
if (!filePath.StartsWith(folderPath))
```

Проверки на `..` перед этим не было вообще — защита держалась только на этой строке.
А она пропускает любую соседнюю папку, чьё имя начинается с имени синхронизируемой:
для папки `C:\data\sync` путь `C:\data\syncbackup\secrets.txt` условие проходит.
Сравнение к тому же шло без `StringComparison`, то есть зависело от текущей культуры.

Достижимо устройством, которому уже разрешена папка. Такое устройство не должно
иметь возможности читать за её пределами.

Тот же изъян в двух других местах: `SyncthingDebugController.GetDebugFile` (там
проверка на `..` была, поэтому оставался только обход через соседнюю папку;
требует роли уровня записи) и `CaseSensitivityWrapper.NormalizePath`.

Все три переведены на `PathContainment` — общий помощник, который канонизирует
пути, сравнивает с разделителем на конце и выбирает чувствительность к регистру по
платформе. 14 тестов, включая обход через соседнюю папку и три варианта подъёма
через `..`.

### Ключ API, зашитый в исходниках

`SyncConfiguration.GuiApiKey` по умолчанию равнялся строке
`syncthing-compatible-key`. До появления авторизации по `X-API-Key` это значение
ни на что не влияло, но теперь оно даёт доступ на чтение к конфигурации папок и
потоку событий.

Установки это не затрагивало: `ConfigXmlService.CreateDefaultConfigAsync`
генерирует ключ через `RandomNumberGenerator`. Открытым оставался единственный
путь — агент, который не смог прочитать `config.xml` и работает на значениях по
умолчанию. Теперь ключ в этом случае генерируется для каждого экземпляра.

## Найдено, не исправлено

### Desktop принимает любой TLS-сертификат

Два места:

- `App.axaml.cs:113` — `RemoteCertificateValidationCallback = static (_, _, _, _) => true`
- `MainWindowViewModel.cs:61` — `DangerousAcceptAnyServerCertificateValidator`

Причина в комментарии указана честно: Syncthing по умолчанию использует
самоподписанные сертификаты. Но принимается **любой** сертификат, а не конкретный
известный. Тот, кто находится между Desktop и агентом, читает трафик целиком,
включая `X-API-Key`. На `localhost` это неважно, при подключении к удалённому
серверу по HTTPS — важно.

Правильное решение — закрепление сертификата: запомнить отпечаток при первом
подключении и сверять его дальше, как это делает сам Syncthing с идентификаторами
устройств. Требует места в интерфейсе для подтверждения нового отпечатка, поэтому
вынесено отдельно.

### Анонимная загрузка конфигурации

`GET /rest/system/ui-language` помечен `[AllowAnonymous]` и на каждый вызов
выполняет `_configXmlService.LoadAsync()` — полное чтение и разбор `config.xml`.
Замер в этой же сессии показал, что загрузка конфигурации занимала до 2,6 секунды.
Без авторизации и без ограничения частоты это дешёвый способ нагрузить агента.
Отдаётся при этом одно поле — язык интерфейса.

Напрашивается кеширование значения в памяти с обновлением по событию от
наблюдателя за файлом.

## Проверено и признано корректным

**Обход путей в REST.** `DatabaseController.Browse` и `GetFile` отсекают `..` и
абсолютные пути, затем канонизируют и сверяют префикс **с разделителем**. Сделано
правильно, в отличие от трёх мест выше.

**Пароли.** `JsonFileUserStore` использует BCrypt с настраиваемым work factor —
и при создании, и при смене, и при миграции из `appsettings`.

**Рукопожатие кластерного ключа.** `ClusterKeyService` сравнивает HMAC через
`CryptographicOperations.FixedTimeEquals`, ограничивает частоту запросов,
проставляет срок жизни вызова и удаляет просроченные. Анонимность эндпоинтов
`challenge`/`verify` здесь необходима по устройству протокола.

**Секреты в репозитории.** Автоматический поиск присвоений вида
`password/secret/apikey/token = "..."` не дал ни одного попадания в исходниках.

**Слабая криптография.** MD5, SHA-1, DES, RC2, 3DES не используются нигде.

**Небезопасная десериализация.** `BinaryFormatter` и `TypeNameHandling`
отсутствуют.

**SQL.** Все запросы параметризованы. Две интерполяции в `SqliteSyncDatabase`
подставляют не пользовательский ввод, а имена таблиц из фиксированного массива и
ключи `PRAGMA` из словаря в коде.

**`Random` вместо криптографии.** Все 11 попаданий — идентификаторы запросов,
джиттер повторов и перемешивание порядка загрузки. Секретов среди них нет.

**CORS.** `SetIsOriginAllowed(_ => true)` включается только в среде Development.
В остальных случаях список источников берётся из конфигурации, иначе разрешён
только `localhost`.

**Swagger.** Публикуется только в Development.

**Секрет JWT.** В Development генерируется случайный, в остальных средах
отсутствие или длина меньше 32 символов приводит к отказу при запуске.

**Прочие анонимные эндпоинты.** `ping`, `version`, `health` отдают версию, время
и статус. Пригодно для снятия отпечатка, чувствительных данных нет.

**Токены в логах.** Закрыто ранее в этой сессии: `SensitiveQueryStringEnricher`
вырезает `access_token` и родственные параметры из строки запроса.

## Что стоит проверить отдельно

Не входило в эту проверку и требует своего прогона:

- Уязвимости в зависимостях (`dotnet list package --vulnerable`).
- Права на файлы `config.xml`, `users.json` и `cert.pem` — сейчас они лежат в
  профиле пользователя, но права нигде явно не выставляются.
- Ограничение частоты на API в целом. Оно есть только на входе (`LoginRateLimiter`)
  и на кластерном рукопожатии.
- Заголовки безопасности отдаются, но `Content-Security-Policy` среди них нет.
